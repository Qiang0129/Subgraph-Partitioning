## 一、目标与已确认需求

### 1. 项目目标

开发一个在 Windows 本机运行的科研复合图切分系统，以 **ReAct 智能体的自主工具调用与反馈修正**为核心，完成：

**上传原图 → 理解面板结构 → 提出切分方案 → 实际试切 → 检查完整性 → 自动返修 → 疑难转人工 → 导出结果。**

重点解决文字、坐标轴标签、图形主体被截断，以及共享标题归属不清等问题，同时保留现有方法在常规图片上的良好表现。

切分质量优先于速度与 API 成本，允许分钟级处理。准确率和人工复核率的数值门槛，待建立标准答案、完成首轮实测后共同确定。

### 2. 已确认范围

| 事项 | 第一版要求 |
|---|---|
| 输入 | PNG、JPEG 原始复合图，从原图重新切分 |
| 图片范围 | 当前这类生物医学科研复合图 |
| 切分粒度 | 带字母标注的顶层面板，保留面板内部的小图组合 |
| 处理规模 | 单图试切，以及一次约 50–500 张的批量任务 |
| 自动化 | 自动分析、检查和返修；不确定结果交人工处理 |
| 共享标题 | 完整另存，并记录与相关面板的关联 |
| 人工操作 | 缩放原图、拖拽裁框、增删面板、修改标签、调整共享标题关联、预览和确认 |
| 结果用途 | 同时支持人工阅读、资料整理及后续 AI 信息抽取 |
| 模型 | 用户自行配置外部视觉 API；第一版要求支持视觉输入与原生工具调用 |
| 接口协议 | Chat Completions、Responses |
| 供应商配置 | 借鉴 CC Switch 的配置与切换方式，由本系统独立管理 |
| 模型训练 | 第一版不训练或微调专用模型 |
| 部署 | 启动脚本运行本地网页，暂无硬性截止时间 |

这里的 **ReAct 指 Agent 的 Reasoning + Acting 方法**。前端可以采用 React，但它与 ReAct 是两个独立的技术选择。

第一版不包含论文 PDF 提图、面板内部的进一步拆分、不规则遮罩编辑、多人账户及服务器部署。

## 二、技术架构与 Agent 方案

### 1. 推荐技术职责

采用 **Java 业务后端 + Python Agent 与视觉工具 + React 操作界面**。

| 层次 | 技术选择与职责 |
|---|---|
| 前端 | React、TypeScript、Canvas 标注组件；负责上传、任务展示、裁框编辑与复核 |
| Java 后端 | Java 21、Spring Boot；负责业务 API、供应商配置、批次队列、结果管理和导出 |
| Agent 服务 | Python 3.12、LangChain、LangGraph；实现 ReAct 工具调用、状态流转、返修和人工暂停／恢复 |
| 图像工具 | Pillow 负责裁切，OpenCV 负责几何和图像分析，PaddleOCR 作为首选本地 OCR 引擎 |
| 持久化 | 本地文件保存图像产物；Java 业务库与 Python 工作流检查点分别使用独立 SQLite 数据库 |
| 服务通信 | 本机 HTTP 接口；前端通过 Java API 操作，进度通过 SSE 推送 |

本机已核对到 Java 21、Node 22、64 位 Python 3.12，以及约 16 GB 内存。首版按 CPU 图像处理加外部模型推理设计，不要求本地 GPU。

Python 依赖使用独立环境。PaddleOCR 的 Windows 安装、模型下载和 CPU 推理表现列入最早的环境验证关卡。

**首版不强制引入 LangChain4j、LangGraph4j。** Agent 编排集中在 Python，避免维护两套智能体运行时；Java 保持业务主后端的定位。

### 2. LangGraph 与 ReAct 的分工

LangGraph 管理整个任务的状态、预算、检查点、异常和人工介入；ReAct 在允许的工具范围内，自主决定下一步观察与行动。

建议的外层流程：

```text
输入检查与图像规范化
        ↓
ReAct 分析原图、调用工具、提出切分方案
        ↓
确定性裁切并生成候选预览
        ↓
几何检查 + 文本边界检查 + 视觉完整性复核
        ├─ 通过 → 保存可交付版本
        ├─ 可修复 → 携带具体问题返回 ReAct
        └─ 不确定或预算耗尽 → 暂停并进入人工复核
                                      ↓
                              保存人工修改并重新检查
                                      ↓
                                  确认与导出
```

这是一个包含分析、复核等职责的工作流。第一版采用单个 ReAct 执行核心，复核节点使用独立上下文，暂不增加多智能体协商系统。

### 3. Agent 工具集

Agent 通过预定义工具操作图片，不开放任意脚本或系统命令执行。

| 工具能力 | 作用 |
|---|---|
| 查看整体结构 | 获取缩略图、尺寸和坐标映射 |
| 查看局部区域 | 放大标签、边缘、共享标题和疑似截断位置 |
| 检测文本 | 返回文字内容、文本区域及方向信息 |
| 分析图像结构 | 提供留白、连通区域、边缘和布局候选等辅助证据 |
| 提交布局候选 | 输出面板标签、矩形框、共享区域及关联关系 |
| 实际试切 | 按原始像素坐标生成子图和边界预览 |
| 执行检查 | 返回越界、文本相交、疑似截断、遗漏与内容混入等问题 |
| 局部修改方案 | 调整指定面板或共享区域，保留未受影响的部分 |

工具返回的坐标统一映射到处理图像的原始分辨率，避免把缩略图或局部放大图的坐标直接用于裁切。

### 4. 质量检查与返修

检查分为三层：

- **确定性检查**：坐标是否合法、矩形是否为空、标签是否重复、文件是否生成、输出是否与记录的坐标一致。
- **内容风险检查**：裁框是否穿过文本区域，边缘是否存在疑似被截断的文字或图形，是否出现可疑遗漏、重叠或邻图混入。
- **视觉语义复核**：结合原图、候选布局、实际子图及邻近上下文，判断面板完整性与共享区域归属。

OCR、几何规则和模型意见都作为检查证据，不能单独作为“切分正确”的证明。视觉复核不能只看裁好的子图，否则容易忽略已被裁掉的内容。

返修必须针对具体问题修改，并保留前后版本。系统需要识别无效修改、反复改回等情况，及时转人工。

初始资源限制采用可配置默认值：

- 同时处理 2 张图，本地 OCR 单工作进程。
- 每张图最多进行 3 轮自动返修。
- 每张图最多 24 次模型请求，最长运行 10 分钟。
- 达到任一上限后转人工复核；网络重试和格式修复计入调用预算。

这些是运行保护参数，首轮实测后可以调整，不作为准确率承诺。

### 5. 模型配置与兼容性

配置页提供供应商名称、接口地址、API Key、协议、模型名称、超时和并发设置。

每份配置启用前必须测试：

1. 基本连通性与认证。
2. 视觉输入是否真实有效。
3. 原生工具调用及工具结果回传。
4. 结构化结果的解析与校验。
5. 响应中可用的用量信息。

不满足视觉或工具调用要求的配置，明确显示不兼容，不能仅凭接口返回成功就启用。

Chat Completions 和 Responses 分别实现协议适配，并统一为内部的图像输入、工具调用、工具结果和最终布局接口。模型输出必须经过结构校验，不能直接作为文件操作指令。

API Key 由 Java 侧加密保存，前端不回显完整密钥，日志脱敏。任务记录供应商、模型与配置版本，便于复现。

## 三、数据、接口与操作流程

### 1. 输入与坐标约定

- 原图只读保存，并记录文件名、尺寸和 SHA-256。
- JPEG 的 EXIF 方向在处理副本中统一，保存与原始文件的映射。
- 所有裁框使用处理图像上的整数像素坐标：`[x1, y1, x2, y2)`。
- 模型使用的缩略图和局部图必须带坐标转换信息。
- 子图从确定的图像像素裁出，不通过生成模型补字、补图或重绘。
- 如果原图本身已经截断或无法辨认，标明来源限制，进入人工处理。

切分不要求把整张图强制分成完全覆盖、互不重叠的网格。背景留白可以不输出；重叠和未覆盖区域需要结合内容归属判断。

### 2. 核心数据对象

第一版至少包含：

| 对象 | 核心信息 |
|---|---|
| 批次 | 输入清单、执行配置快照、进度、统计和状态 |
| 原图 | 来源、哈希、尺寸、处理副本与方向映射 |
| 布局版本 | 版本号、面板、共享区域、检查结果和确认状态 |
| 面板 | 稳定 ID、原始标签、裁框、文件路径和共享区域关联 |
| 共享区域 | 标题等区域的裁框、图片及关联面板 |
| 检查问题 | 类型、严重程度、位置、关联面板、证据与处理状态 |
| 执行记录 | 工具动作、简要决策说明、耗时、用量、错误与重试 |

保留大小写标签。标签缺失、重复或识别不清时，进入复核，不自动编造可信标签。

现有 44 组结果可以作为标注草稿和基线导入；旧绝对路径按文件名映射并核对来源。它们不直接成为标准答案，也不作为新增的“旧结果自动修复”产品入口。

### 3. 接口边界

Java 对外提供三组主要 API：

- **任务接口**：创建批次、查询进度、取消、重试、恢复及导出。
- **复核接口**：获取原图与候选布局、保存修改、确认结果、重新检查。
- **供应商接口**：配置管理、能力测试、可用状态和模型选择。

Python 提供内部执行、状态查询、暂停、恢复和取消接口。

Java 负责业务状态，Python 负责工作流检查点；双方通过接口同步，不直接修改对方数据库。任务恢复复用已提交产物，避免从头重跑整批。

### 4. 人工复核界面

复核页同时提供：

- 原图与候选裁框叠加显示。
- 当前子图预览及问题清单。
- 面板、共享标题和关联关系编辑。
- 修改前后的版本对照。
- 保存、重新检查、确认和继续执行。

进入人工复核后，暂停该图的自动修改。人工保存与 Agent 写入使用版本检查，防止覆盖用户刚完成的调整。

页面显示工具动作、发现的问题及简要决策说明，不要求展示模型内部思维过程。

### 5. 导出约定

每张原图的导出目录包含：

- `layout.json`：带版本号的结构化布局、来源、坐标及关联关系。
- `preview.png`：面板与共享区域边界预览。
- `panel_标签.png`：面板图片。
- `shared_编号.png`：完整共享标题等区域。
- `check_report.json`：检查结果与确认状态。

批次导出 ZIP 和汇总报告。正式结果仅包含自动通过或人工确认的版本，未解决项在报告中列出；草稿允许单独导出并明确标记。

输出使用相对路径，避免重复出现旧 D 盘绝对路径带来的迁移问题。

## 四、开发阶段与交付关卡

| 阶段 | 主要工作 | 进入下一阶段的条件 |
|---|---|---|
| **P0：环境与接口验证** | 建立独立环境；验证两种模型协议、视觉输入、工具调用、OCR 和裁切链路 | 能完成“看图—调用工具—回传观察—输出合法布局—实际裁切”的最小闭环 |
| **P1：数据与标注基础** | 建立 Java／前端骨架、供应商配置、图片管理和矩形编辑；导入现有结果为草稿 | 用户能够逐图确认 46 张原图，保存标准答案及共享标题关联 |
| **P2：视觉工具与基础切分** | 实现坐标映射、OCR、局部观察、布局候选、确定性裁切和基础检查 | 普通图及 14、15、a2 等代表性问题有可复现的输入、输出与检查记录 |
| **P3：ReAct 自动返修** | 接入有约束的工具选择、视觉复核、局部修正、预算控制和人工暂停 | 能修复已知问题；无法解决的问题能明确转人工；正常结果不会被无依据反复修改 |
| **P4：批处理与完整复核** | 完成 50–500 张任务队列、进度推送、取消恢复、版本管理、人工确认和导出 | 任务中断、服务重启及局部失败不会导致整个批次丢失 |
| **P5：质量门槛锁定与独立验收** | 完成回归评测，锁定阈值和配置；对独立新图验收 | 质量、人工复核率及资源消耗达到双方在实测后确定的标准 |
| **P6：本机交付** | 提供启动／停止脚本、环境检查、依赖锁定、使用说明和故障定位说明 | 在本机按说明可重复启动，完成上传、切分、复核、恢复和导出 |

优先证明 Agent 闭环对切分质量有实际帮助，再完善批量交互和交付包装。

拟将工程放在当前资料目录下的独立 `subfigure-agent` 子目录中；原图、旧切分目录和压缩包保持原状。运行产物与人工标准答案单独管理。

## 五、评测、验收与默认边界

### 1. 标准答案与评测数据

- 现有 46 张原图作为标注、开发与回归数据。
- 现有 481 张子图只是旧结果数量，不预设为标准答案的面板总数。
- 标准答案包含面板标签、完整裁框、共享区域及关联，并对关键截断风险区域作标记。
- 独立新图建议首批准备 20–30 张，覆盖不同布局、文字密度、图像类型和共享区域情况。
- 新图在模型配置、提示词和验收规则锁定后评测；参与调试后，应转入回归集，不能继续当作未见数据。

### 2. 核心指标

| 指标 | 用途 |
|---|---|
| 面板识别精确率与召回率 | 检查多切、漏切和标签识别 |
| 面板内容完整正确率 | 检查文字、图形、坐标轴及必要信息是否保留完整 |
| 整图成功率 | 检查一张原图是否全部切对，包括共享区域关联 |
| 自动通过结果正确率 | 检查系统是否错误地放行了问题图 |
| 人工复核率 | 防止通过把所有图片都交人工来获得表面上的高质量 |
| 返修净收益 | 比较修正了多少问题、又引入了多少新问题 |
| 耗时与调用消耗 | 评估批量处理可用性 |

框坐标 IoU 作为辅助指标，不能替代内容完整性判断。

费用在供应商价格已配置、用量信息完整时估算；信息缺失时标为未知，不记作零成本。

### 3. 必须覆盖的验收案例

- **图 14**：培养皿底缘完整，邻接面板不再错误带入其底部内容。
- **图 a2 的 d**：斜排横轴标签完整保留。
- **图 15**：共享标题完整另存并正确关联，不切碎或误归属。
- **图 45、46**：没有旧切分结果，也能从原图独立处理。
- 常规图片经过自动检查与返修后不新增明显错误。
- 大小写标签、低清文字、倾斜文本、不同尺寸和 JPEG 方向处理正确。
- 遇到缺失标签、无法辨认内容或矩形难以独立表达的布局，能转人工并说明问题。
- API 超时、限流、认证失败、工具参数错误和结构化结果错误均有可定位状态。
- 任务取消、重启恢复、人工修改和导出版本保持一致。
- 已导出的子图与记录坐标对应的图像区域逐像素一致。

基线比较需要区分：现有结果共同覆盖的 44 张切分质量，以及全部 46 张的处理覆盖率。

同时比较“单次视觉提案”和“完整 ReAct 检查返修闭环”，确认新增复杂度确实带来质量收益。

### 4. 质量门槛制定方式

按已确认的选择，不提前承诺未经验证的准确率。

完成标准答案和首轮试验后：

1. 汇总基线、单次提案与完整闭环的表现。
2. 分析错误类型、误放行情况及人工处理量。
3. 共同锁定自动通过正确率、整图成功率和人工复核率门槛。
4. 固定运行配置，再进行独立新图验收。

最终验收同时报告样本量与适用范围。少量新图通过，不能推导为所有科研图都具有同样准确率。

### 5. 当前计划边界

本计划已纳入对齐后的 ReAct 含义、技术职责、模型接口、切分范围、人工处理和验收方式，达到可进入分阶段实施的需求完整度。

仍需通过实测确定的是数值质量门槛、最终并发与预算参数，以及具体模型的实际表现；这些均已设置明确的验证阶段和确认关卡。

计划形成时尚未创建工程、修改材料文件或更新记忆文件。后续实施状态以工程内的实际代码、测试结果和进度记录为准。
